# 텔레그램 그룹방 — 세 축, 그리고 승인이 1:1 전용인 이유 (#1003)

> 형님 결정(2026-09-18): BStockReport 가 1:1 방에 매핑된 건 **의도가 맞다.** 다만
> **다른 사용자는 그룹방에 매핑하길 원할 수 있으니 기능적으로 지원**되어야 한다.

"그룹방이 되는가"는 하나의 답이 아니다. **코드로 재 보면 세 축으로 갈리고, 축마다 답이 다르다.**

| 축 | 그룹방 | 상태 |
|---|---|---|
| **인바운드** (그룹 메시지 → 제품) | ✅ 된다 | 코드 변경 0. 그룹 `chat_id` 로 **바인딩만 만들면** 붙는다 |
| **아웃바운드** (제품 → 그룹) | ✅ 된다 | 2026-09-22부터. 바인딩의 `selection` 이 목적지다 (아래 §2) |
| **승인 탭** (인라인 버튼) | ❌ **안 된다 — 의도적으로** | 그룹에서는 탭이 거부된다 (아래 §3) |

---

## §1 인바운드 — 설정 문제지 코드 문제가 아니다

`plugin/telegram/webhook.py` 는 `chat.id` 를 그대로 싣고 **`chat_type` 필터가 없다.**
그룹 `chat_id`(음수)로 `resource_binding` 을 만들면 그룹 메시지가 그 제품으로 들어온다.

## §2 아웃바운드 — 목적지는 **바인딩**이 정한다

`delivery_config` 는 **커넥터 계정**의 것이다. 그래서 한 계정(= 봇 하나)에 묶인
**모든 제품이 같은 방으로** 갔고, 제품별로 방을 나누려면 `chat_id` 를 하나 더 담으려고
**봇 토큰을 하나 더** 만들어야 했다.

이제 디스패치가 이렇게 병합한다:

```
{**account.delivery_config, **binding.selection}
```

좁은 쪽이 나중이다 — 바인딩은 **한 제품 × 계정 쌍**에 대해 말하고, 계정은 그 전부에 대해 말한다.

* **빈 `selection`(기본값)은 아무것도 안 바꾼다.** 압도적 다수의 행이 이 경우다.
* **두 소비자가 이 값을 읽는다** — 이벤트 빌더와 플러그인 컨텍스트. 둘은 한 이름을
  같이 읽는다. 한쪽만 병합하면 이벤트는 그룹방으로 가는데 플러그인은 1:1 설정으로 도는
  반쪽 배선이 된다.
* **`resource_bindings` 에는 (제품, 계정) 유니크 제약이 없다.** 한 쌍에 행이 둘이고
  **서로 다른 방**을 가리키면, 목적지가 행 순서에 좌우된다. 그래서 그런 경우에는
  **오버라이드를 버리고** 계정의 설정을 쓴다 (`connector_delivery_ambiguous_binding_selection`
  로그). 배송은 되돌리기 어려우니 **추측하지 않는다.** 행이 둘이어도 **값이 같으면**
  정상 적용된다 — 중복 자체는 모호함이 아니다.

> 📏 **켤 때 이게 no-op 이었다는 기록.** 2026-09-22 prod 의 살아 있는 바인딩 셋은
> **전부 `selection` 이 자기 계정의 `delivery_config` 와 값이 같았다.** 즉 이 기능을
> 켜도 배송 한 건도 움직이지 않는다. 그 사실은 PR 설명이 아니라
> `test_todays_prod_shape_is_a_no_op` 에 테스트로 박혀 있다.

> ⚠️ **`selection` 은 인바운드 라우팅 힌트도 겸한다** — `intake.py` 가 여기서
> `artifact_type` 을 읽고 dict 를 통째로 페이로드에 싣는다. 목적지 키가 인바운드
> 페이로드에도 실린다는 뜻이다(이 변경 전에도 이미 그랬다). 빌더는 자기가 모르는 키를
> 무시하므로 배송에는 영향이 없다.

> 🧭 **github 는 이 규칙 밖이다.** `deliver_github` 는 `GithubBinding` 을 받고, 그건
> **제품 자신의 `repo_url`** 로 계정을 고른다(#681/#684/#723) — `resource_bindings` 를
> 아예 안 본다. 이미 제품별로 갈리는 **다른 메커니즘**이라 여기로 끌어오지 않았다.

## §3 승인 탭 — 그룹에서는 거부된다. 그게 맞다

`backend/connectors/telegram_callback.py`:

```python
if parsed.get("chat_type") != "private":
    return False
```

**1:1 에서는 `from.id == chat_id` 가 곧 신원 증명이다.** 그 방에는 형님과 봇 둘뿐이다.

**그룹에서는 그 등식이 깨진다.** `chat.id` 는 음수 그룹 id 이고 `from.id` 는 **탭한 사람의
개인 id** 다. 둘은 절대 같지 않다. 그래서

* `chat_type` 게이트만 풀면 비교식이 **항상 거짓**이 되어 여전히 거부되고,
* 비교식까지 손대면 **그룹의 아무나 승인할 수 있게 된다.**

지금은 **`chat_id` 하나가 "어디로 보내나"와 "누가 승인할 수 있나"를 겸하고** 있고,
그룹 승인을 지원하려면 그 둘을 갈라야 한다.

### 형님 결정 (2026-09-22): **가르지 않는다**

**그룹 = 배송 전용**(인바운드 + 아웃바운드), **승인 = 1:1 전용.** 코드 변경 0.

이미 그렇게 동작하고 있었지만 **어디에도 적혀 있지 않아서**, "그룹 승인이 왜 안 되지"를
조사하는 데 시간이 두 번 쓰였다. 이 문단이 그걸 막으려고 있다.

검토했다가 **안 고른** 안(다시 필요해지면 여기서 출발하면 된다):

| | 무엇 | 왜 안 골랐나 |
|---|---|---|
| A | 커넥터 계정에 `authorized_user_ids` 허용목록 | 새 **보안** 설정 키가 생기고, **비었을 때의 기본값이 곧 보안 기본값**이다(반드시 거부여야 한다). 그룹 멤버 여러 명에게 승인권을 주려면 이 안뿐이다 |
| B | 그룹에는 승인 탭을 아예 **안 보낸다** | 코드가 적고 보안 모델이 안 바뀐다. ⚠️ 이 안의 값어치는 *그룹 메시지에 버튼이 실제로 렌더되는가* 에 달려 있는데 **안 쟀다** — 안 실린다면 C 와 차이가 없다 |
