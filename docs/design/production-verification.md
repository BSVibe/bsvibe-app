# 프로덕션 검증 설계 — 증명은 머지에서 끝나면 안 된다

> 2026-08-10. 형님 지적에서 출발: *"애초에 최소치만 검증할 거면 CI 쓰면 되지 BSVibe를 쓸 이유가 없잖아."*
> 반박할 게 없다. 이 문서는 그 간극을 메우는 설계다.
>
> ⚠️ **개정 (2026-08-10, 형님)**: 초판은 "머지 → 배포 → 프로브"였다. **틀렸다.**
> 머지·배포 후 검증은 **이미 오염된 뒤**다. 검증은 **일회용 환경을 띄워 거기서, 머지 전에** 돌아야
> 한다. 그래야 형님이 그 증거를 보고 승인한다. 이름도 "프로덕션 검증"이 아니라
> **전 표면 검증(full-surface verification)** 이 맞다 — 문제는 *어느 환경이냐*가 아니라
> *사용자 표면까지 실제로 돌렸느냐*였다.

## 1. 문제

BSVibe의 검증(선언된 계약 + 파생 게이트)은 **정직하다** — 2026-08-09~10 이틀간 거짓 `PROVED`는
한 번도 나오지 않았다. 문제는 정직성이 아니라 **주장의 범위**다.

게이트의 주장 = **"이 레포가 자기 검사를 통과했다"**
필요한 주장 = **"배포된 시스템에서 이 변경이 의도대로 동작한다"**

앞의 것은 CI가 이미 한다. 그것만 할 거면 BSVibe를 쓸 이유가 없다.

그리고 이건 이론이 아니다. 이틀간 프로덕션 결함 **6건**을 잡았는데 **전부 유닛 green**이었고,
전부 **E2E를 손으로 돌려서만** 드러났다:

| # | 결함 | 유닛 상태 |
|---|---|---|
| #716 | 게이트 box가 서버 run 경로를 가리킴 | green (테스트가 답을 인자로 넣어줌) |
| #717 | 파생기에 "변경 없음" 거짓 단언 | green |
| #718 | 인프라 실패가 "게이트 부재"로 위장 | green |
| #719~721 | client_attach가 딜리버러블을 못 만듦 | green |
| #722 | 500자 조용한 절단 → 숫자 날조 | **green (버그가 명세로 박혀 있었음)** |
| #723 | 한 커넥터 실패가 전체 dispatch 중단 | green |

게이트가 돌았어도 전부 `PROVED`가 나왔을 것이다. bsvibe-app의 스위트가 green이었으니까.

## 2. BSVibe가 CI보다 할 수 있는 것 (이미 가진 부품)

CI는 ephemeral 러너 안에서 **코드만** 본다. 배포된 시스템도, 실제 워커도, 실제 커넥터도 못 본다.
BSVibe는 다르다 — 부품은 이미 다 있고 **연결이 안 돼 있을 뿐이다**.

| 부품 | 현재 용도 | 프로덕션 검증에서의 역할 |
|---|---|---|
| 워커 `action="exec"` (#702) | in-place 게이트 명령 | **임의 머신에서** 배포 후 프로브 실행 |
| `github_merge_watch` + MergeWatchWorker | 머지 감시·자동머지 | 머지 → **배포 감지 → 프로브** 로 연장 |
| MCP 툴 표면 | 형님이 BSVibe를 조작 | **BSVibe가 자기 제품 표면을 사용자처럼 두드림** |
| Safe Mode·커넥터·Decision | 산출물 전달 | 프로브 결과를 형님에게 |
| `/api/health` → `git_sha` | (플레이스홀더) | **무엇이 배포됐는지** 판별 |

## 3. 설계

### 3.1 환경은 **체크의 필드**이지 새 상태가 아니다

처음엔 `proof_state`를 `PROVED_BUILD` / `PROVED_PROD`로 쪼개려 했다. **틀렸다** (형님 지적, 2026-08-10).

현행 모델이 이미 답을 갖고 있다:
- `work_steps.proof_state` = `UNTESTED` / `PROVED` / `REFUTED` — **집계된 판정 하나**
- `VerificationResult` = run당 **여러 행**, 각각 `outcome`(PASSED/FAILED/INCONCLUSIVE) + `contract` + `result`
- 어디서 돌았는지는 **이미 체크 레벨에 있다**: `result.derived_gate.origin` =
  `"derived"`(서버 샌드박스) vs `"derived_in_place"`(파운더 머신), 그리고 `execution_target`

상태를 쪼개면:
- **조합 폭발** — build 통과 + prod 실패는? staging/canary가 생기면? `REFUTED`도 쪼개야 하나?
- **중복** — `origin`이 이미 답하는 걸 enum에 다시 인코딩
- **리포트 입장에선 어차피 같은 항목들의 집합이다.** 체크 하나 = `{무엇을 · 어디서 · 결과}`.
  BUILD냐 PROD냐는 **"어디서"라는 필드값**이지 다른 종류의 것이 아니다.

∴ 프로덕션 프로브는 **`VerificationResult` 행을 추가할 뿐**이다 (`origin="production_probe"` +
명시적 `surface` / `environment`). 리포트는 한 목록으로 균일하게 렌더한다. 프로브 실패는 이미 있는
`REFUTED`(또는 Decision)로 표현된다. **새 상태는 필요 없다.**

### 3.2 프로브는 **그 제품의 사용자 표면**에서 검증한다

빌드 게이트가 *레포 매니페스트*에 grounding 하듯, 프로덕션 프로브는 **제품의 전달 표면**에 grounding 한다.
"브라우저를 쓸 것인가"는 잘못된 질문이다. 올바른 질문은
**"이 제품의 사용자는 무엇을 통해 가치를 받는가, 거기서 확인했는가"**다.

| 제품 | 사용자 표면 | 프로브 수단 |
|---|---|---|
| BSVibe PWA | 웹 화면 | 브라우저 자동화 (Playwright 등) |
| BStockReport | **텔레그램 메시지** | **Telegram API** |
| CLI 도구 | 터미널 | CLI 실행 |
| API 제품 | HTTP | HTTP 클라이언트 |

**BSVibe는 이 정보를 이미 갖고 있다** — 커넥터 바인딩이 "이 제품의 산출물은 텔레그램 chat X로 간다"를
안다. 제품 metadata + 바인딩이 표면 선언이고, 프로브 저작 LLM은 거기에 grounding 한다.

⚠️ **API가 멀쩡한 것이 UI가 멀쩡하다는 뜻은 아니다.** API 레벨만 검증하면 그걸 소비하는 화면에서
깨진 경우를 배제할 수 없다. (2026-08-09~10 결함 6건이 전부 백엔드였다는 사실은 **표본 편향**이다 —
UI에서만 깨지는 결함은 애초에 그 목록에 오를 수 없었다. 손E2E가 백엔드만 두드렸으니까.)

**표면별 예 — #722 절단**: 올바른 프로브는 DB의 `summary` 길이가 아니라
**텔레그램에 실제로 도착한 텍스트에 `$922,010`과 `이상징후`가 있는가**다. 그게 사용자가 받는 것이다.
DB를 봤다면 "저장은 됐네"로 넘어갔을 수 있다.

### 3.2.1 이미 절반은 하고 있다 — `docs/e2e/` 체크리스트

레포의 `docs/e2e/`에는 **사람이 따라 하는 마크다운 체크리스트**가 쌓여 있다
(`executor-really-gets-its-tools-checklist.md`, `connector-reconnect-oauth-checklist.md` 등).
즉 **검증안을 LLM이 산문으로 쓰는 일은 이미 일어나고 있다.** 문제는
**아무도 실행하지 않고 결과가 어디에도 남지 않는다**는 것.

∴ 진짜 간극은 "LLM이 안을 못 낸다"가 아니라 **"안이 실행 가능한 형태가 아니다"**다.
이 체크리스트들을 실행 가능한 프로브로 **승격**시키는 것이 가장 값싼 출발점이다.

### 3.2.2 LLM이 저작하되, LLM이 판정하지 않는다

파생 게이트가 신뢰받는 이유는 *"명령의 exit code가 판정이고 모델의 의견이 아니다"* 이다.
프로덕션 프로브가 "LLM이 앱을 보고 잘 되는 것 같다고 말함"이 되면 그 성질을 잃는다.

Playwright 스크립트도, Telegram API 호출도 **실패하면 non-zero로 죽는다**. LLM은 스크립트를
**작성**하고, 판정은 여전히 **exit code**가 한다. 계약은 그대로, 도구만 표면별로 다르다.

⚠️ **하네스가 없으면 LLM은 지어낸다.** 현재 파생기 프롬프트는 "레포가 선언하지 않은 도구를 지어내지
마라"고 명시한다. bsvibe-app에는 **Playwright가 없다**(PWA는 vitest + testing-library뿐). 지금
브라우저 프로브를 시키면 올바르게 거부하거나 나쁘게 지어낸다. **표면별 하네스가 먼저다.**

### 3.3 검증 환경 — 일회용 스택, 머지 **전**

프로브는 **변경이 실제로 돌아가는 온전한 스택**을 필요로 한다. 그 스택은 prod가 아니라
**그 run을 위해 띄웠다가 버리는 환경**이다.

프리미티브는 이미 있다: `docker compose -f deploy/compose.yaml up -d` 하나로
postgres · redis · backend · worker · pwa · sandbox-dind 가 전부 뜬다.

흐름:
```
run 작업 완료 → 일회용 스택 기동(그 브랜치 코드) → 전 표면 프로브 실행
             → 결과를 VerificationResult 로 기록 → 스택 파기
             → 형님이 그 증거를 보고 승인 → 머지
```

이 순서가 주는 것:
- **오염 없음.** 깨진 코드가 prod에 닿기 전에 판정된다.
- **run 수명 문제 없음.** 검증이 run 안에서 끝난다 — 배포 인프라에 묶이지 않는다.
- **부작용 격리.** 텔레그램 등 외부 발신은 테스트 채널/스텁으로 향한다.
- **승인의 근거가 생긴다.** "유닛 통과"가 아니라 "실제로 띄워서 사용자 표면까지 돌려봤다".

### 3.3.1 🚨 같은 머신에 두 번째 스택을 띄우는 것은 **프로덕션을 죽일 수 있다**

`deploy/compose.yaml` 현재 상태에서 그대로 스택을 하나 더 올리면:

| 충돌원 | 값 | 결과 |
|---|---|---|
| `container_name: bsvibe-sandbox-dind` | **고정 이름** | prod에서 돌던 그 컨테이너와 충돌 — 프로젝트명을 바꿔도 소용없다 |
| 호스트 포트 | `5442` `6387` `8700` `3700` | 바인딩 충돌 |

메모리에 *"container_name 충돌로 스택다운"* 실사고가 있다. 검증 환경은 반드시:
- **고정 `container_name` 제거** (검증용 오버레이에서 무효화)
- **호스트 포트를 아예 발행하지 않는다.** 프로브는 compose 네트워크 **안에서** 돈다
  (브라우저 프로브 포함) — 그러면 포트 충돌 자체가 없다
- **파기 보장** — `down -v` 를 finally 로. Mac Mini 디스크 풀은 복구불능 브릭이다(메모리 기록)

### 3.3.2 스택을 **어떻게** 띄우는가 — 유도 기본, 제품 metadata 오버라이드 (형님, 2026-08-10)

제품마다 "인스턴스 하나"의 의미가 다르다. bsvibe-app 은 `docker compose up` 이지만
BStockReport 는 CLI 라 **스택 자체가 없다**(환경 = 레포 + `.env`).

∴ **표면과 같은 구조**로 간다:
- **기본은 레포에서 유도.** 파생 게이트가 매니페스트에서 검사 명령을 유도하듯,
  `compose.yaml` / `Makefile` / `package.json` 등에서 기동·파기 방법을 유도한다.
- **제품 metadata 가 오버라이드.** 특수한 제품은 `execution_target` / `client_workspace_path`
  옆에 기동·파기 명령을 명시할 수 있다.

> ✅ **개정 반영 완료 (§3.3.2.1)**: 초판의 "유도할 게 없으면 스택 없음" 분기는 **삭제**됐다.
> compose 가 없어도 **레포가 선언한 툴체인이 컨테이너를 지목**한다(`uv.lock`/`pyproject.toml` →
> uv 이미지, `package.json` → node, `go.mod`, `Cargo.toml`). `None`(= 호스트 실행)이 남는 경우는
> 둘뿐이다: ①레포가 **아무 툴체인도 선언 안 함**(재현할 것이 없음) ②제품이 **명시적으로 선언**
> (`verify_stack: null` — 호스트 자원이 정당히 필요한 검사). 즉 호스트 실행은 이제 **선언의 결과**이지
> 유도 실패의 부산물이 아니다.

### 3.3.2.1 ⭐ 검증 실행은 **컨테이너로** — 에이전트 실행과 다른 요구다 (형님, 2026-08-10)

초판의 "compose 있으면 스택, 없으면 `None`(스택 없음)"은 **부족하다.** 형님 지적:
기술 스택 고립과 의존성 재현을 위해 CLI 제품에도 컨테이너가 필요하다.

**구분해야 할 두 실행**:

| | 에이전트 실행 | 검증 실행 |
|---|---|---|
| 요구 | 파운더의 기존 디렉터리에서 네이티브 — client_attach 의 존재 이유 | **재현 가능 · 격리** |
| 현재 | 네이티브 ✅ | 네이티브 ❌ |

지금 BStockReport 검증은 `uv run pytest` 를 파운더 머신에서 돌린다. 그래서:
- **의존성 재현 불가** — 그 `.venv` 상태를 모른다. 누가 `pip install` 한 게 있으면 검증 결과가
  변경과 무관한 이유로 달라진다. `uv.lock` 이 있어도 venv 는 드리프트한다.
- **격리 없음** — 표면 프로브의 스텁 서버가 localhost 포트를 쓰고, 잘못 설정되면 파운더의 진짜
  `.env`(Alpaca 키)에 닿는다.
- **툴체인 전제** — 파운더 머신에 맞는 Python/uv 가 있어야만 검증이 성립한다.
- **정리 안 됨** — 남은 프로세스·파일이 파운더 작업 트리를 오염시킨다.

**§3.5 프라이버시 계약과 충돌하지 않는다** — 컨테이너를 **파운더 머신에서** 띄우므로 소스는 그 머신을
떠나지 않는다. client_attach 가 네이티브인 것은 *에이전트의 편집*에 관한 규정이지 검증까지 그래야
한다는 뜻이 아니었다.

**설계가 오히려 단순해진다**:

> **모든 제품이 검증 환경을 갖는다.** 어떻게 만드는지가 유도된다 — compose 파일이 있으면 compose,
> 없으면 레포가 선언한 툴체인으로 **일반 컨테이너**를 짓는다.

"스택 없는 제품"이라는 특수 케이스가 사라진다. (§3.3.2 의 `None` 분기는 이 방향으로 개정해야 한다.)

⚠️ **정직한 한계**: BStockReport 의 `.env` 에는 `BLOASIS_DB_PATH` — **파운더 머신의 로컬 SQLite 경로**가
있다. 컨테이너는 마운트 없이 그걸 못 본다. 즉 **일부 검사는 정당하게 호스트 자원을 필요로 한다.**
"전부 컨테이너"가 아니라 **선언의 문제**다 — 재현 가능한 검사는 컨테이너에서, 호스트 자원이 필요한
검사는 그렇다고 명시하고 호스트에서. 섞어놓고 모르는 것이 최악이다.

**비용**: 이미지 레이어 캐시를 전제로 짧게 (형님). 콜드 빌드만 길고, 그건 부팅 예산(§3.3.4)으로 덮는다.

```
       && tar -cf - -C <workspace> --exclude=./.venv '--exclude=*/.venv'
              --exclude=./node_modules '--exclude=*/node_modules' .
          | docker exec -i <slot> tar -xf - -C /work
exec : docker exec -w /work <slot> sh -lc <command>
down : docker rm -f <slot>          # 없으면 exit 0 — 슬롯 회수가 곧 스택 회수
```

세 가지 설계 판단:
1. **바인드 마운트가 아니라 tar 복사.** ①검증이 파운더 작업 트리를 **쓰지 않는다**(에이전트가
   일하는 그 디렉터리다) ②docker VM 이 어느 호스트 경로를 공유하는지에 의존하지 않는다.
   실측: BStockReport 2.4MB 복사 + 컨테이너 기동 **1.3초**.
2. **`.venv`/`node_modules` 는 절대 안 들어간다.** macOS 네이티브 바이너리가 리눅스 컨테이너
   안에 있으면 **"프로비저닝된 것처럼 보이는 깨진 환경"** 이 된다. 중첩(`apps/*/node_modules`)까지
   막으려면 glob 이 필요하고, 복사가 워크스페이스를 cwd 로 돌기 때문에 **반드시 quote** 해야 한다.
3. **`plan.wrap(cmd)` 이 유일한 진입 seam.** 컨테이너를 띄워놓고 명령은 호스트에서 돌리면
   격리한 것이 없으면서 격리했다고 주장하게 된다. 그래서 wrap 은 `StackReady` 의 **메서드**이고
   docker 컨텍스트 고정까지 같이 한다(호출자가 잊을 수 없게).
   ⚠️ 고정은 `env VAR=… cmd` 접두가 아니라 **shell export** 다 — 기동이 파이프라인이라
   `env` 접두는 **첫 프로세스에만** 붙는다. 절반만 고정된 것은 고정 안 된 것이다.

**음성 대조 완료**: `_UNCOPYABLE` 를 비우면 실 docker 테스트가 실패한다(확인함). 문자열 비교가
아니라 **진짜 데몬에 대고 돌리는 테스트**라 이게 가능하다.

#### ⚠️ `.env` 는 컨테이너에 들어가지 않는다 (PR #731, 실측 근거)

BStockReport 로 실제 재보고 정한 것이다:

| 환경 | 결과 |
|---|---|
| 파운더 머신(진짜 `.env`) | **FAIL** — `test_config.py::test_defaults` 가 기대한 기본값 대신 실 Alpaca 키를 읽음 |
| 컨테이너 + `.env` 복사 | **FAIL** (같은 이유 — 앰비언트 상태를 그대로 옮겼으니 당연하다) |
| 컨테이너, `.env` 제외 | **148/148 PASS** |

즉 `.env` 는 ①검사 결과를 변경과 무관한 이유로 좌우하는 **앰비언트 호스트 상태**이고
②**크리덴셜 표면**이다(그 키를 읽는 검사는 진짜 주문을 낼 수 있다 — §4 규칙 4). 그래서 복사에서
뺀다. 호스트 설정이 정말 필요한 검사는 **선언**한다(`verify_stack: null`) — 사고로 도착해선 안 된다.

단 dotenv **기본 파일만** 거른다. `.env.prod` 를 이름으로 로드하는 레포는 다른 것을 선언하는
것이고, `.env.example` 은 따라가야 한다(`--exclude=./.env` 가 `.env.example` 을 안 삼키는 것은
실 tar 로 확인함 — 우리가 아니라 tar 가 패턴을 매칭하므로 실측 외에는 알 방법이 없다).

### 3.3.3 동시 실행 슬롯 — 개수는 **DB 설정**, 고아는 슬롯 회수로 함께 치운다 (형님, 2026-08-10)

**슬롯 수는 워크스페이스 설정으로 DB에 둔다** (env 상수가 아니라). 형님 의도: 나중에
**요금제 티어**로 쓸 수 있다 — "동시 검증 N개"가 곧 플랜 차이가 된다.

⚠️ **동시 실행 제한만으로는 고아가 안 치워진다.** run 프로세스가 죽으면 `finally` 가 돌지 않아
스택이 남고, 그 슬롯을 **영구 점유**해 결국 검증이 아예 못 돌게 된다.

**해법 — 슬롯 회수가 곧 스택 회수**:
1. 슬롯 `i` 를 **PG advisory lock** 으로 잡는다. 이 레포에 이미 있는 패턴이다
   (`backend/workflow/infrastructure/lease.py`, `pg_try_advisory_lock` + SQLite 폴백).
   **세션 스코프라 run 프로세스가 죽으면 락이 자동 해제된다 — TTL 관리가 필요 없다.**
2. compose 프로젝트 이름을 **슬롯 번호로** 짓는다(`verify-slot-<i>`, run id 가 아니라).
3. 슬롯을 잡은 쪽은 **먼저 `down -v` 를 돌린다**(멱등). 이전 점유자가 남긴 게 있으면 그때 치워진다.

∴ **별도 리퍼 워커가 필요 없다.** 슬롯을 되찾는 행위가 곧 이전 스택을 파기하는 행위다.
정상 종료 경로의 `finally` `down -v` 는 그대로 두되, 그것에 **의존하지는 않는다**.

### 3.3.4 기동은 게이트 명령과 **별도 타임아웃 예산** (형님, 2026-08-10)

`verify_gate_command_timeout_s` 는 900초인데 **콜드 빌드는 이를 넘길 수 있다**
(autodeploy 의 실제 빌드가 수 분 걸린다). 기동은 성격이 다른 작업이므로 자체 예산을 갖는다.

초과 시 **거짓 실패가 아니라 인프라 실패로 fail-closed 기록**한다 — §4 규칙 3(부재는 스스로를
증명해야 한다)의 적용이다. "스택을 못 띄웠다"와 "띄웠는데 프로브가 실패했다"는 다른 사실이다.

### 3.4 프로브는 어디서 도는가 — 검증 대상 **바깥**, 지금은 **논리적** 분리

스택이 깨지면 그 안의 프로버는 **침묵한다**. 침묵은 성공과 구별되지 않는다.
∴ 프로브 실행 주체는 검증 대상 밖에 있어야 한다.

**실행 주체 = 호스트 워커(`mac-mini-e2e`).** 이 워커는 컨테이너가 아니라 **네이티브 macOS
프로세스**(launchd)다. 그래서 prod가 죽든 검증 스택이 죽든 워커는 살아서 **에러를 보고**한다 —
침묵이 아니라 fail-closed. `docker` 도 워커 PATH 에 있다(`/opt/homebrew/bin/docker`).

기각한 대안:
- **prod backend 컨테이너가 실행** — 프로버가 망가질 수 있는 대상 *안*에 있게 된다. 요구사항
  정면 위반이고, docker 소켓 노출은 사실상 호스트 root 권한이다.
- **sandbox-dind 안에서 중첩** — 진짜 격리라 #724 오버레이가 불필요해지지만, sandbox-dind 는
  **prod 의 공유 자원**이다(autodeploy 주석: recreate 하면 in-flight verify run 을 죽인다).
  검증하려다 다른 run 을 죽인다. 중첩 docker 의 비용·DinD 방화벽도 부담. 후일 재검토.

**물리적 분리가 아니라 논리적 분리다** (형님, 2026-08-10). 물리 자원이 하나뿐이라 같은 머신을
쓰는 것이고, 이상적으로는 분리된다. 그 논리적 경계를 구성하는 것은:
①#724 오버레이(container_name · 호스트 포트 · 이미지 태그) ②아래의 docker 컨텍스트 고정.
BSVibe 는 이미 **원격 워커 등록**을 지원하므로, 검증 전용 머신을 워커로 붙이면 **설계 변경 없이**
물리적 분리로 승격된다. 지금 선택이 막다른 길이 아니라는 뜻이다.

남는 한계: 같은 머신이라 디스크·CPU 를 prod 와 경합하고, 머신 레벨 장애는 둘 다 못 본다.

### 3.4.1 ⚠️ docker 컨텍스트는 **명시 고정**해야 한다

`docker` 의 대상 선택은 **전역 가변 사용자 상태**다. 다른 프로필을 띄우는 것만으로
(`colima start palworld`) 현재 컨텍스트가 바뀌고, 그 뒤의 모든 비고정 `docker` 호출이 엉뚱한 VM 을
가리킨다. 2026-08-10 실제로 발생 — `docker ps` 가 "No such container" 를 내서 prod 가 죽은 줄
알았으나 prod 는 멀쩡했고 컨텍스트만 palworld 였다.

검증 스택이 이걸 밟으면 **비결정적 검증 환경**이 된다. 충돌은 안 나서 "안전해 보이지만" 프로브가
다른 VM 의 스택을 두드리고, 컨텍스트가 도로 바뀌면 같은 코드가 실행마다 다른 환경을 검증한다.
우리가 없애려는 바로 그 부류의 거짓 결과다.

- `_infra` 의 `autodeploy.sh` / `watchdog.sh` / `backup.sh` 는 **이미** `export DOCKER_CONTEXT=colima`
  로 고정하고 있다(확인 완료).
- 그러나 **워커 exec 은 그 env 를 물려받지 않는다.** `_handle_exec_task` 는 워커 프로세스의 env 를
  상속하는데, 워커 launchd plist 에는 `DOCKER_CONTEXT` 가 없다. ∴ 스택 명령을 만들 때 **명시적으로**
  넣어야 한다.
- ⚠️ `DOCKER_HOST` 가 `DOCKER_CONTEXT` 를 **이긴다**. 환경에 `DOCKER_HOST` 가 새어 있으면 컨텍스트
  고정이 조용히 무시되므로, exec env 에서 그것까지 통제한다.

### 3.5 `git_sha` 는 게이트가 아니라 운영 위생으로 강등

초판은 `/api/health` 의 `git_sha` 를 배포 감지 게이트로 삼았다. 머지 전 검증으로 바뀌면서
**게이트로서는 불필요**해졌다. 다만 "지금 prod에 뭐가 떠 있나"는 여전히 알아야 하므로 고칠 가치는 있다:
`compose.prod.yaml` 은 `${GIT_SHA:-prod}` 인데 autodeploy 폴러가 `GIT_SHA` 를 넘기지 않아 항상 `"prod"` 다.

### 3.3.6.1 ⚠️ 시임을 만들 때 **소비자가 무엇을 보는지**를 단언하라

#743 은 conflict 뒤 `git merge --abort` 를 했다. 근거는 리퍼(#736)가 머지 중인 트리를
영원히 거부한다는 것이었고, 나는 그 추론을 **테스트로 박았다**
(`test_a_conflicted_merge_is_aborted_before_the_worktree_goes_back`). green 이었다.

틀렸다. 그 충돌 상태가 **인계 그 자체**다 — 에이전트는 그 안에서 해결해야 base 를 조상으로
갖는 커밋을 만든다. abort 된 트리를 받은 에이전트는 "충돌 마커가 없습니다, 이미 해결됐습니다"
하고 손으로 고쳐 **선형 커밋**을 만들었고, PR 은 영원히 dirty 로 남았다(run `7442c185`).

∴ **테스트가 green 이라는 사실은 내 추론을 검증해주지 않는다.** 시임의 양쪽 중 *소비자* 쪽이
무엇을 필요로 하는지로 단언해야 한다. 리퍼 걱정 자체도 거꾸로였다 — 머지 중인 트리는
미해결 작업이 있는 트리이고, 거부는 안전장치가 도는 것이다.
→ [[boundary-test-must-not-supply-the-answer]]

### 3.3.6.2 ⚠️ "커밋할 게 없다" ≠ "push 할 게 없다"

#745. `commit_and_push_run_work` 는 인덱스가 비면 push 전에 반환했다. 그런데 **에이전트가
스스로 커밋하는 경로가 있고, conflict 지시문이 바로 그걸 시킨다.** 그 경로에서 머지 커밋이
파운더 머신에 3커밋 앞선 채 갇히고 github 은 영영 못 봤다(run `0ef554ca`).

일반화: **한 상태 질문의 답을 다른 질문의 답으로 재사용하지 마라.** 여기선 "이 함수가 커밋을
만들었나"가 "이 브랜치에 보낼 것이 있나"를 대신하고 있었다.

### 3.3.6.3 ⚠️ 정상적인 기다림이 장애 알람이 되면 안 된다

Decision 위에 파킹된 런은 의도적으로 `RUNNING` 이다(`drive_once` 가 OPEN 만 집으므로).
ops 워치독은 `running/open` 2시간+ 를 wedge 로 읽었다. ⇒ **형님이 2시간 안에 답을 안 하면
그 기다림이 "🚨 프로덕션 이상 감지"가 되어 30분마다 폰을 쳤다.** 답을 기다리는 사람에게
제품이 고장났다고 알리는 구조.

처방: 대기 중인 Decision 이 있는 런을 wedge 후보에서 제외(`_infra` `430b74d`). 그것이
"이 기다림은 의도된 것"이라는 **서버 자신의 기록**이라 정직한 판별자다. §3.3.5.1 이
"도달해야 할 것이 안 왔다"였다면 이건 **"오지 말아야 할 것이 왔다"** — 같은 축의 반대쪽 끝이고,
둘 다 형님이 폰을 보고 짚었다.

### 3.3.6 ⚠️ 격리는 **앰비언트 조건을 제거**한다 — 그 조건이 검사의 주제라면 컨테이너에서 증명 못 한다

위 run 의 작업은 *"`test_defaults` 가 파운더의 실제 `.env` 를 읽어서 실패한다. 앰비언트 `.env` 에
의존하지 않게 고쳐라"* 였다. 게이트는 컨테이너에서 통과했다. 그런데 **컨테이너에는 `.env` 가 없다** —
즉 이 게이트는 고친 것과 아무것도 안 한 것을 **구별할 수 없었다.** (실제로 호스트에서 따로 돌려 통과를
확인했고, 수정은 옳았다. 하지만 그건 내가 손으로 한 것이지 게이트가 증명한 게 아니다.)

일반화하면: **재현 가능한 환경은 정의상 호스트의 우연을 지운다. 그래서 "호스트의 우연에 견디는가"를
묻는 검사는 그 환경에서 무의미하게 통과한다.** §3.3.2.1 의 "호스트 자원이 필요한 검사는 선언한다"와
같은 동전의 뒷면이고, 규칙 1([[boundary-test-must-not-supply-the-answer]])의 환경판이다 —
검증이 자기가 답을 넣어준 셈.

∴ 표면 하네스(5~7)를 설계할 때 **그 프로브가 무엇을 관측 가능하게 만드는지와 동시에 무엇을 관측
불가능하게 만드는지**를 같이 적어야 한다. 지금 아는 한계: 컨테이너 검증은 (a) 앰비언트 설정 의존성
(b) 파운더 머신 고유 자원 (c) 호스트 툴체인 드리프트 를 **관측할 수 없다**.

## 4. ⭐ 프로브 설계 규칙 (이틀간 실제로 밟은 함정에서)

### 규칙 1 — 프로브가 답을 스스로 넣으면 안 된다
제 배포 확인은 `grep "_github_actions"` 였다. 그건 **코드가 거기 있는지**만 본다.
게다가 그 grep 자체가 거짓 양성을 냈다(`grep -c ... || echo 0` → `"0\n0"` ≠ `"0"`).
→ [[boundary-test-must-not-supply-the-answer]]

### 규칙 2 — 제품 표면을 통한 **결과**를 단언하라, 코드 존재가 아니라
#723의 올바른 프로브는 *"`_github_actions`가 파일에 있는가"* 가 아니라
**"Safe Mode 항목을 승인하면 텔레그램 액션이 성공하는가"** 였다.

### 규칙 3 — 부재는 스스로를 증명해야 한다
"아무 문제 없음"과 "관측 자체가 실패함"을 구분하라. 프로브가 대상에 닿았다는 것부터 증명한다.
→ #718이 정확히 이 교훈이다.

### 규칙 4 — 부작용은 Safe Mode 모델을 따른다
프로덕션 프로브 중엔 실제 부작용을 내는 것이 있다(진짜 텔레그램 발송 등).
`output_mode=safe` / 전용 테스트 채널로 감싼다.

### 6.0 첫 테스트 대상 = BStockReport 주간 리포트 (형님, 2026-08-10)

트랙이 완성되면 **첫 실증은 BStockReport 주간 리포트 흐름으로** 한다.
새 시나리오를 지어내지 않고 **이미 완전히 파악된 업무**로 재는 것이 가장 정확하다.

이 대상이 특히 좋은 이유:

1. **정답을 안다.** 결정적 도구(`bstockreport run --emit`)가 verbatim 블록을 만들고,
   그게 텔레그램에 그대로 도착해야 한다. 기대값이 모호하지 않다.
2. **실패 모드를 이미 겪었다.** 이 흐름에서 실제로 터진 결함이 둘 있고, 둘 다
   **프로브가 잡아야 할 것의 교과서적 예**다:
   - #722 — 500자 절단으로 `$922,010` → `$922,0` **날조**. 올바른 프로브는 DB가 아니라
     **텔레그램에 도착한 텍스트**에 `$922,010`과 `이상징후`가 있는지 본다.
   - #723 — github 전달이 client_attach 런에서 죽으며 dispatch 전체를 중단시켜
     **아무것도 전달되지 않음**. 올바른 프로브는 "승인 → 텔레그램 액션 succeeded".
3. **음성 대조가 공짜다.** 두 결함의 커밋을 되돌린 상태로 프로브를 돌리면
   **프로브가 실패해야 한다**(§6 PR 7). 인위적으로 버그를 심을 필요가 없다 —
   실제 회귀 커밋이 이미 히스토리에 있다.
4. **표면이 웹이 아니다.** 첫 사례가 텔레그램이라 "표면은 제품마다 다르다"는 설계 전제를
   처음부터 강제한다. 브라우저를 특별대우하지 않게 된다.

∴ PR 5(Telegram 하네스)와 PR 7(음성 대조)이 이 대상 하나로 함께 실증된다.

#### ✅ 음성 대조 1차 결과 (2026-08-11)

BStockReport 의 표면 하네스(`tests/surface/`, 스텁 텔레그램 + 도착 텍스트 단언)에 #722 회귀를
그대로 주입해 봤다. 파운더 트리는 건드리지 않고 scratch 복사본에서.

| 조건 | 결과 |
|---|---|
| 그대로 | **3 passed** (양성 대조) |
| `send_telegram` 에 `text[:500]` 절단 주입 | **FAIL** — "청크 분할 안 됨: 스텁이 1개만 수신" |
| `text[:5000]` 절단(청크는 여러 개로 남김) | **FAIL** — `received == report` 위반, *"청크 분할 후 리포트가 잘렸습니다!"* |

세 번째가 핵심이다. **청크 개수 같은 프록시가 아니라 도착 텍스트 전체 동일성**이 잡았다 —
DB 를 봤다면 "저장은 됐네"로 넘어갔을 그 결함이다.

⚠️ **범위의 정직한 한계**: 이 하네스는 **BStockReport 자신의 전달 경로**를 검증한다. #722 의 실제
절단은 **BSVibe 딜리버러블 파이프라인**에 있었으므로, 그건 BSVibe 표면에서 별도 프로브가 필요하다
(제품의 표면 검사가 플랫폼의 결함을 대신 잡아주지 않는다).

### 6.1 브라우저 하네스의 전제 (PR 6에서 반드시 함께)
- **인증** — 지속적인 **테스트 아이덴티티**. (오늘 세션이 MCP OAuth로 막혔던 그 벽)
- **부작용 격리** — 전용 테스트 제품/채널. 일회용 스택이라 자연히 격리되지만 외부 발신은 별도.
- **flakiness 정책** — 흔들리는 프로브의 거짓 실패는 신뢰를 무너뜨리고, "green 될 때까지 재시도"는
  **fail-open** 이다. 재시도 규칙을 명시하고 quarantine 을 둔다.

## 7. 결정된 것 (2026-08-10, 형님)

**Q. 프로브를 누가 쓰는가 → 작업 에이전트가 직접. 단 TDD 순서로 검증안이 먼저.**
버그를 쓴 에이전트가 그 버그를 통과시키는 검증을 쓰는 문제는 **순서로 푼다** — 작업 전에 검증안을
먼저 내놓게 한다. 코드가 없는 시점이라 버그에 맞춰 검증을 뜯어고칠 수 없다.

⚠️ **다만 순서가 덮지 못하는 잔여**: "버그에 맞춰 검증을 고치는 것"은 막히지만
**"검증이 자기 입력을 스스로 넣는 것"** 은 안 막힌다. #716이 그 예다 — 먼저 썼어도
`acquire(id, "/founder/path")` 라고 썼을 것이다. 저자가 **호출자가 무엇을 넘기는지 잘못 알고 있었기**
때문이지 순서 문제가 아니다. 그건 **실제 호출자로 돌려보는 것**(= 이 문서의 표면 프로브)이 깬다.
∴ **TDD 순서 + 표면 프로브가 같이 있어야 덮인다.** 둘 중 하나로는 부족하다.

**Q. 프로브 실패 시 행동 → 이미 정의돼 있다.**
클로드 코드와 동일: 검증 실패 → 피드백 → 수정 → 재검증 반복. `_drive_loop` 가 이미 그렇게 돌고,
`gate_failure_is_actionable()`(#718)이 "실제로 RAN 하고 failed 한 것만 피드백"을 보장한다.
별도 롤백 정책 불필요. **머지 전 검증이므로 run 안에서 루프가 닫힌다.**

**Q. 프로덕션 프로브의 빈도/비용 → 질문 자체가 소멸.**
build/prod 구분이 사라졌으므로 카테고리 결정이 아니다. "어떤 체크가 이 변경에 필요한가"만 남고
그건 저작 시점에 정해진다.

## 8. 트랙 C — 증거의 정의를 표면별로 (2026-08-13 형님 지목, 2026-08-14 착수)

> 형님 문제 제기: *"지금 프로젝트가 너무 코드 쓰기에 매몰된 건 아닐까. 애초에 bsvibe 는
> 비개발 작업도 대응하려고 만들었는데."* 코드로 확인한 결과 **맞다.**

### 8.1 간극은 한 문장이다 — 두 절반이 서로에게 미룬다

게이트 파생기는 산문 산출물을 **명시적으로 다른 경로에 넘긴다**:

> `gate_derivation.py:165-167` — "If the change is not something a command can verify
> (pure prose / design / a doc), set `applicable` to false and return no commands —
> that is a valid, honest answer; **the judge and demonstration paths cover it.**"

그런데 demonstration 경로는 **코드 파일이 아니면 쳐다보지도 않는다**:

```python
# verification_service.py:1029-1038
for path in written_paths:
    if not _is_code_path(path) or _is_test_path(path):   # ← _CODE_EXTS 18개 확장자
        continue
    ...
if not sources:
    return None          # ← 산문/데이터 산출물은 여기서 조용히 끝난다
```

∴ **아무도 안 맡는다.** 파생기는 "demonstration 이 커버한다"며 비키고, demonstration 은
`.md` 를 보고 `None` 을 낸다. 결과가 `demonstrated=False` + `gate_discovered=False` =
**등급 D**, 그리고 매니페스트 있는 레포면 `gate_expected=True` → **매번 사람을 부른다.**

### 8.2 I2 기계는 이미 표면 중립이다 — 막는 건 입구 하나뿐

`outcome_demonstration.py` 전체에 코드 특정 개념이 **하나도 없다.**
`Probe(command, expect_exit_zero, expect_stdout_contains)` + `judge_probe` 의
결정론적 비교뿐이다. 플래너 프롬프트조차 이미 *"call the function, run the built artifact,
**hit the endpoint, grep the produced file**"* 라고 쓰여 있다.

**즉 C 는 새 축을 만드는 일이 아니다** (핸드오프 예측 적중). `demonstrated` 다리의
**공급원을 늘리는 일**이고, 대부분의 작업은 이미 만들어져 있다.

### 8.3 ⚠️ 이 확장의 급소 — 규칙 1 위반이 기본값이다

산문 산출물을 그냥 플래너에 넣으면 프로브가 이렇게 나온다:

```
grep -q "Executive Summary" report.md      # 자기가 쓴 걸 자기가 확인 — 항상 통과
```

**모든 산문이 자동으로 등급 B 를 받는다.** 이건 지금의 과잉 파킹보다 **나쁘다** —
래칫이 무너지고, 정직성 사다리가 거짓말을 시작한다. (§4 규칙 1 ·
[[boundary-test-must-not-supply-the-answer]] · [[unit-test-supplies-what-production-withholds]])

**처방 — 플래너를 산출물 텍스트에 대해 눈멀게 한다.**
산문 산출물의 기대치는 **작업 문장(intent)에서만** 나온다. 플래너는 생성된 텍스트를 보지
못한 채 "이 작업이 제대로 됐다면 산출물에서 관측돼야 하는 것"을 선언하고, 프로브가 산출물을
검사한다. 이건 §7 형님 결정(*"TDD 순서로 검증안이 먼저"*)을 산문 표면에 그대로 적용한 것이고,
규칙 1 을 **구조로** 만족시킨다 — 베낄 원본이 손에 없다.

코드 경로는 그대로 소스를 본다(거긴 API 를 알아야 프로브를 쓸 수 있고, 실행이 판정하므로
베끼기가 통하지 않는다). **표면마다 그라운딩이 다르다** — 그게 §3.2 의 원래 주장이다.

### 8.4 `surface_exercised` — ⚠️ 초안이 틀렸다 (2026-08-14 착수 시 코드 확인)

`gate_derivation.surface_exercised()` 는 "레포가 선언한 **표면** 체크가 RAN 하고 PASSED
했는가"를 이미 판정해 blob 에 기록한다(`verification_service.py:989`,
`inplace_gate.py:286/308`). 사다리는 그걸 안 읽는다.

**초안은 "정의상 이것이 I2 다, 배선 하나면 된다" 였다. 코드를 보니 아니다.**

I2 플래너에게 하는 **첫 지시**가 이것이다:

> `verification_service.py:268` — "You are an INDEPENDENT outcome-demonstration verifier.
> **You do NOT re-run the author's tests** and you do NOT give an opinion."

**저자로부터의 독립성이 I2 의 정의**다 — 느슨하게 저작된 intent 테스트를 통과하며 쓰레기가
"verified" 를 받던 것(Q-2)이 I2 를 만든 이유다. 그런데 `kind:surface` 는 정의상
**레포가 선언한 자기 체크**이고, 파생기는 그걸 *고르기만* 할 뿐 내용은 레포의 것이다:

> `gate_derivation.py:159` — "if the repo **DECLARES** checks that drive its delivered
> behaviour … A declaration is a marked/named suite, a build target, or a script
> **the repo itself defines**"

∴ **그 런에서 에이전트가 방금 그 스위트를 썼다면 자기 채점이다.** 선택은 독립적이지만
내용은 아니다. 그대로 배선하면 "통과하는 표면 테스트를 하나 쓰면 등급이 오른다"가 되고,
그건 I2 가 막으려고 존재하는 바로 그 구멍이다.
→ [[unit-test-supplies-what-production-withholds]] · [[boundary-test-must-not-supply-the-answer]]

**남은 선택지 (형님 판단 필요)**
1. **런에서 저작되지 않은 표면 체크만** 이 다리를 벌게 한다 — 체크가 가리키는 파일이
   `written_paths` 에 없을 때만. 독립성을 되찾지만 판정이 복잡해지고, "이 런이 그 체크를
   건드렸나"를 명령 문자열에서 파일로 되짚는 것이 결정론적이지 않을 수 있다.
2. **사다리에 안 넣는다.** 증명 표면에는 이미 보이므로 사람이 읽을 수 있고, 등급은
   독립 관측(I2)에만 근거한 채로 둔다. 가장 정직하지만 §8.4 의 값어치가 사라진다.
3. **다리를 하나 더 만든다** — A/B/C/D 위가 아니라 옆에. 구조 변경이라 래칫을 다시 봐야 한다.

⚠️ **그대로 배선하는 선택지는 없다.**

### 8.5 🔴 착수 순서를 바꾼다 — 래칫 절반은 a 와 얽혀 있다

b(흡수분)의 자연스러운 처방은 `gate_expected` 를 *레포* 속성에서 *작업* 속성으로 옮기는
것이다(산문만 바뀐 작업 → 게이트 기대 안 함 → 파킹 안 함). **그런데 이걸 먼저 하면 회귀가 난다.**

`_drive_loop` 는 툴 호출 없는 턴을 "작업 끝"으로 읽는다. 지금 명세만 쓰고 멈춘 턴은
등급 D 파킹에 **걸려서** 사람이 구해준다. 래칫을 먼저 풀면 그 턴은 파킹 대신
**조용히 `verified` 로 종료**된다 — 조용한 조기 완료는 과잉 파킹보다 나쁘다.

∴ **C 안에서의 순서**: ①증거 공급 확대(등급을 *올리기만* 함, fail-open 0) →
②래칫 완화(항목 a 와 함께). 형님의 "C 부터" 는 유지하되, C 의 안전한 절반부터 간다.
이 회귀는 **항목 a 가 C 와 직교하다는 핸드오프 주장의 반례가 아니라 그 이음매**다 —
오늘의 과잉 파킹이 조기 완료를 가려주고 있었을 뿐이다.

### 8.7 🔴 실증이 잡은 것 — 답을 계산해놓고 버리는 프로브 (2026-08-14)

C1 의 첫 라이브 런 `e72689e8` 은 목표를 달성했다 — 산문 산출물이 **등급 B** 로 통과하고
`review_ready` 로 끝났으며 **Decision 0건**(대조군 `0bbf72eb` 은 D ×2 + 파킹 ×2).

**그런데 프로브를 뜯어보니 6개 전부 `expect_stdout_contains` 가 비어 있었고, 둘은
실패할 수가 없었다:**

```
python -c "...; print(''.join(sorted(set(g for g in 'ABCD' if g in c))))"   # 항상 exit 0
python -c "...; print('found' if ex else 'missing')"                        # 항상 exit 0
```

문서에 A/B/C/D 가 하나도 없어도 빈 문자열을 찍고 exit 0 → `matched`.
**답을 계산해놓고 버렸다.** 6개 중 2개가 무조건 통과였고 등급은 구분하지 못했다.

§4 규칙 1 의 사촌이다 — 답을 *넣은* 게 아니라 **아무것도 단언하지 않았다.** 모듈 docstring 은
이미 *"declares the literal observation that MUST appear"* 라고 말하는데, 파서가 생략을
허용하고(`expect_stdout_contains` 기본 `()`) 프롬프트가 강제하지 않았다.

**처방(C1b)**: artifact 표면에서 단언 없는 프로브는 **실행 전에 버린다**(`drop_unasserted`).
단언 = 기대 substring **또는** `expect_exit_zero=False`(실패해야 하는 명령은 성공으로
반증되므로 falsifiable). 버려서 남는 게 없으면 정직하게 `undemonstrable`.
버리는 것은 등급을 **낮추기만** 하므로 구멍을 열 수 없다.

⚠️ **코드 표면에는 적용하지 않았다.** 같은 공백이 있지만 거긴 demonstration 이 **게이팅**이라,
프로브를 버리면 통과가 사람 호출로 바뀐다 — 이 트랙이 줄이려는 바로 그것. **별건 판단**이고,
테스트로 그 결정을 고정해뒀다(`test_the_code_surface_keeps_its_unasserted_probes_for_now`).

**교훈**: 프로브가 *돌았다*는 것과 프로브가 *무언가를 걸 수 있었다*는 것은 다르다.
`matched` 개수는 후자를 증명하지 않는다. → [[boundary-test-must-not-supply-the-answer]]
