## §0 — 먼저 읽어라: **prod 의 모든 런이 프레이밍에서 죽는다**

#966 이 배포된 지금도 **런은 완주하지 못한다.** 프레이밍 LLM 턴이 호스트 워커에서 행(hang) 나고,
백엔드는 frame 콜러의 300초에 포기한다. #966 은 *행이 나도 슬롯이 8분 묶이지 않게* 만들었을 뿐
**행 자체를 없애지 않았다.**

원인 추적에서 **아래를 전부 실측으로 배제**했다(#965 코멘트에 표로 있다). 다시 하지 마라:

| 가설 | 검증 | 결과 |
|---|---|---|
| CLI 자체 | 같은 인자 형태로 직접 실행 | ✅ 2.4s |
| 인증(만료 베어러) | 워커의 `_subprocess_env_with_bearer()` 를 그대로 사용 | ✅ 2.1s |
| `--model sonnet` | 모델 지정 | ✅ 2.6s |
| 프롬프트/시스템 내용 | **행 난 태스크 행의 바이트를 그대로 replay** | ✅ 3.8s |
| launchd 최소 env | HOME·PATH 만 있는 env 로 실행 | ✅ 2.3s |
| stdin 미종료 | `claude_code.py` write→drain→close | ✅ 정상 |

⇒ **invocation 은 무죄.** 워커 프로세스 안에서만 재현된다.

**남은 단서 A**: 두 번의 행 모두 **워커 재시작 직후 첫 태스크**였다(12:11→12:27, 14:10→14:29).
성공했던 chat 턴(09-14)은 3일 떠 있던 프로세스의 것이다. 표본 2+2라 단정은 못 한다.

**남은 단서 B (#970)**: CLI 를 돌릴 때마다 stderr 로 나오는 커넥터 비활성 경고 —
*"claude.ai connectors are disabled because ANTHROPIC_API_KEY or another auth source is set…"*.
토큰 값이 유효하든 더미든 **똑같이 나온다** ⇒ 값이 아니라 **`ANTHROPIC_AUTH_TOKEN` 이 있다는 사실
자체**가 방아쇠다(워커가 `claude_code.py:70-72` 에서 항상 주입). **행의 원인이라는 증거는 없지만**,
정체가 확인되지 않은 유일한 상시 신호다. #968 의 `elapsed_s` 로 커넥터 로딩이 첫 턴에서 시간을
쓰는지 처음 볼 수 있다.

⚠️ **진단 전에 로그부터 조용하게 만들어라 (#970)**: 워커가 **19일째** 5분마다 만료된 refresh 로
400 을 받고 **rich 트레이스백 전체**를 덤프한다. 실측 — 5,754회 · 로그 245MB · **전체 줄의 96.7%가
이 트레이스백**. 이번 추적에서 실제 신호(`task_received` 이후의 침묵)를 찾는 데 가장 큰 방해였다.

**다음 사람이 할 일**: 이번에 넣은 `executor_turn_started` / `executor_turn_first_event`(elapsed 포함)
두 마커로 **세 경우가 한 번의 grep 으로 갈린다** — 프로세스가 안 떴다 / 떴는데 모델이 한 마디도 안 했다 /
중간에 멈췄다. 다음 행 때 그 로그부터 봐라.

### #963 에서 실측으로 드러난 것 (이슈 본문보다 나빴다)
`is_local=false` 퍼블리케이션은 **두 결함이 한 원인**이었다 — 풀 커넥션에 **잔류**(다음 체크아웃이
물려받아 큐 폴러의 fail-open 클레임을 **fail-closed** 로 만든다)와 첫 커밋 이후 **증발**(세션이 다른
커넥션으로 옮겨 레이어 3 이 꺼진다). 이슈는 잔류만 알고 있었다.

⚠️ **워커 프로세스의 임포트 그래프는 `backend.data.rls` 에 닿지 않는다**(실측). 그래서
`workspace_scope` 가 그 모듈을 직접 임포트한다 — 안 그러면 레이어 2 만 켜지고 레이어 3 은 조용히 꺼진다.

### 데이터 변경 1건
고아 `dispatched` executor 태스크 **2건을 `failed` 로 종결**(삭제 아님). `dispatched` 2→0 · `failed` +2 ·
`done` 불변. 2026-06-10 자 `pending` 1건은 **그대로 뒀다** — `pending` 도 좌초한다는 별개 증거.

## §Ⅱ — 새로 연 이슈

* **#964** 배경 루프 나머지 — `settle` 은 **행마다 커밋**이라 지금 구조로 가능(1순위),
  `schedule`·`delivery` 는 **한 트랜잭션에 여러 워크스페이스를 배치**해서 **트랜잭션 분할이 선행**
* **#965** executor 태스크가 한 번 건네진 뒤 **재전달되지 않는다** — 데드라인 절반은 #966 으로 닫힘.
  재전달은 **"워커가 받았다" 신호**(`dispatched`→`running`)가 선행이다. 단순 XAUTOCLAIM 은
  **정상적으로 1시간 도는 act 턴을 중복 실행**시킨다
* **#970** 워커가 19일째 매 5분 OAuth 트레이스백을 덤프한다(로그의 **96.7%**, 245MB) ·
  CLI 커넥터 경고는 **정체 미상**. 재로그인해도 **또 만료되면 반복**되므로 로그/백오프는 별개로 필요
* **#967** `client_worker_manager` 테스트가 부하 있는 CI 에서 흔들린다 — 그리고 그 에러 메시지는
  **'하네스 굶음'과 '행이 안 보임'을 구분하지 못한다**(leak 주입으로 같은 증상 재현: 11 failed / 422s)

## §Ⅴ — 이 세션에서 값을 한 규율

* **🔪 전선 절단이 통과하면 그 테스트는 그 속성을 안 재고 있다.** 마커 "한 번만"을 절단했는데 초록이
  나왔다 — 단언이 리스트의 **존재**만 봤기 때문. 개수로 바꾸니 빨개졌다
* **🧪 부정 대조군을 검사 **안에서** 만들지 마라.** 레이어 3 설치 테스트의 첫 판은 검사 안에서 rls 를
  임포트해 **영원히 초록**이었다. 임포트 전에 `sys.modules` 를 본다
* **📐 "내 머지가 CI 를 깼나"는 같은 커밋 재실행이 가른다** — 로컬 3종 재현 실패 + 재실행 통과로
  #963 무죄. 다만 **첫 실패가 내 머지 커밋에 있었다는 사실 자체는 무시하지 않았다**
* **🩺 배제도 산출물이다.** 프레이밍 행은 못 고쳤지만 6가지를 실측으로 지웠고 표로 남겼다.
  다음 사람의 출발점이 "아무것도 모름"이 아니라 "이 여섯은 아니다"가 된다
* **🔌 호스트 워커는 autodeploy 안 된다** — 이번에도 kickstart 후 **프로세스 시작 시각**으로 확인했다.
  안 했으면 #966 은 배포돼도 **효과 0**이었다(구버전 워커가 payload 를 안 읽는다)
