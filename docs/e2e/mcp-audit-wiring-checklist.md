# E2E 체크리스트 — MCP 쓰기 감사 배선 (#1039)

**무엇**: MCP 쓰기 툴 49개가 `audit_event` 를 선언하는데 prod `audit_outbox` 의
`bsvibe.mcp.*` 가 **0건**이었다. 감사를 REST 와 같은 길로 잇는다.

> 🧭 **이 결함은 어떤 테스트도 깨뜨리지 않았다.** 표면에서 감사가 켜진 것과
> 완전히 똑같아 보였으므로, 고치는 것만으로는 부족하고 **다시 조용해지지 않도록**
> 결과(행이 쌓이는가)를 단언해야 한다.

## A. 배포 전 (로컬 — 완료)

- [x] **원인 두 겹을 분리해 적었다**
      ① prod 의 유일한 `ToolContext(` 생성이 `audit_outbox` 를 안 넘긴다(기본값 `None`)
      ② ⭐ `AuditOutboxLike` 가 요구한 `is_open` 은 **어떤 구현도 세우지 않는다** —
      그 이름은 코드 전체에서 **선언과 검사 두 곳에만** 있었다. 상상 속 인터페이스
- [x] 고침: 없는 프로토콜에 구현을 만들지 않고 **REST 와 같은 길**을 쓴다 —
      `AuditEmitter().emit(event, session=ctx.session)`
- [x] 죽은 프로토콜(`AuditOutboxLike`)과 `ToolContext.audit_outbox` 를 **지웠다**.
      주입하는 곳이 0개였다 — 빈 슬롯을 남기면 다음 사람이 또 기댄다
- [x] **행이 쌓이는 것**을 단언(구조가 아니라 결과): 쓰기 툴 디스패치 → 행 증가
- [x] 행이 **무엇인지** 말한다: `event_type` 이 `bsvibe.mcp.*` 이고 툴 이름을 담는다
- [x] **음성 대조군**: 읽기 툴은 행을 안 남긴다 (전부 찍는 구현은 통과 못 함)
- [x] 선언 집합을 **레지스트리에서** 세고(하드코딩 아님) 크기(≥40) + 되돌리기
      어려운 툴 4개를 이름으로 핀
- [x] 절단 2회: emit 제거 → **2칸**, 읽기 툴에 `audit_event` 부착 → **음성 대조군 1칸**
- [x] CI 명령 전부: ruff · format · lint-imports(6 KEPT) · mypy(598) ·
      **pytest 7,146 passed**

## B. 배포 후 (prod)

- [ ] MCP 쓰기를 **한 번** 하고(예: 바인딩 패치) `audit_outbox` 에
      `bsvibe.mcp.*` 행이 생기는지. ⚠️ **배포 전 개수(0)를 분모로 같이 적어라**
- [ ] 그 행의 `payload` 에 `tool` 과 `client_id` 가 들어 있는지
- [ ] **읽기를 여러 번 해도 안 쌓이는지** — 아웃박스가 잡음으로 차면 아무도 안 본다
- [ ] 릴레이(`relay_worker`)가 그 행을 정상 배송하는지 — 새 `event_type` 접두사다

## C. 안 건드린 것 (의도)

- **페이로드의 풍부함** — 툴 이름 + 행위자 + client_id 까지다. 더 풍부한 페이로드는
  핸들러의 몫이라는 기존 REST 관례를 그대로 따른다
- **`audit_event` 를 선언하지 않은 읽기 툴** — 그대로 둔다. 읽기까지 찍으면
  아웃박스가 잡음으로 차고, 그러면 진짜 쓰기가 묻힌다
- **워크스페이스별 보존 기한(Lift Q1)** — 이제야 이 테이블에 MCP 데이터가 들어오므로
  보존 정책의 대상이 실제로 생긴다. 기한 튜닝은 별건
