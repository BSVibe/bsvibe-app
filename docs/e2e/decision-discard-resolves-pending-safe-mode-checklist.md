## 폐기는 두 문으로 들어오는데 한쪽만 정리했다

| | `runs_discard` (`cancel_run`) | 결정 경로 (`_discard_decision_run`) |
|---|---|---|
| 런 종료 | ✅ | ✅ |
| 워크트리 정리 | ✅ | ✅ |
| **pending Safe Mode 항목 정리** | ✅ | ❌ → **이 PR** |
| pending Decision 정리 | ✅ | ❌ (아래 §남는 것) |

`cancel_run` 의 독스트링이 결함 이름까지 적어놨다 — *"cancelling the run alone leaves
its Summary 확인 필요 card up forever (**orphaned-half**)"*. **그 교훈이 옆 문으로
옮겨가지 않았다.**

## prod 실측 (`e8775e7`, 2026-09-09)

* 결정 경로로 폐기된 런 **3건** (`9ccdaa2f` · `ecb8b004` · `0093fce6`)
* 그중 Safe Mode 항목을 가진 것은 **1건**(`0093fce6`) — **그 1건이 고아가 됐다**
* 형님이 **2분 27초 뒤 손으로** 지웠다
* 나머지 2건은 정리할 항목이 **0개**라 반증이 아니다 ⇒ **기회 1회 중 1회 발생**

⚠️ **현재 상태로는 이 결함이 안 보인다.** 지금 pending 은 **0건**이다 — 형님이 손으로
치우셨기 때문이다. *"지금 0건"* 을 *"결함 없음"* 으로 읽으면 안 되는 사례다. 우회하는
사람이 있으면 증거는 지워진다.

## 고친 방식 — 새 기제가 아니라 링크 하나

`cancel_run` 이 이미 쓰는 헬퍼를 그대로 재사용한다(private → public 승격,
`resolve_pending_safe_mode_items`). 두 번째 사본을 만들면 다음에 또 갈라진다.

**자동 정리는 가르치지 않는다.** 이 헬퍼는 행의 `status`/`decided_at` 만 직접 쓰고
`SafeModeQueue.deny` 를 타지 않는다 — 자동 스윕이 negative knowledge 가 되면 안 되기
때문이다. PR #902 (`DenyKind`) 가 세운 것과 같은 문장이다.

## 남는 것 — 이 PR 이 안 고치는 것

  도 부르는데 결정 경로는 안 부른다. 다만 prod 3건 다 `pending_decisions = 0` 이라
