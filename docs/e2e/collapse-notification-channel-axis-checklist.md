# 알림 채널 축 접기 — 검증 체크리스트

> 2026-08-31. 형님 관측에서 시작했다 — *"텔레그램으로 알림 받는 게 분명 있는데
> 왜 부재라고 하지?"* 재보니 형님이 옳았고, **제 앞선 설명이 부정확했다.**

## 형님은 받고 계셨다 — 다만 한 종류만

두 워크스페이스의 텔레그램 커넥터가 **같은 chat_id** 를 가리킨다. 그래서 어느
쪽에서 보내든 형님 폰에 도착한다. 그런데 매트릭스는 이랬다:

| 이벤트 | 형님 작업 ws (노트 1,685) | admin ws (노트 25) |
|---|---|---|
| `auth_down` | ✅ (**prefs 무관** — `DEFAULT_ON_EVENTS`) | ✅ |
| `needs_you` · `shipped` · `failed` | ❌ | ✅ |
| `triggered` · `daily_brief` | ❌ | ❌ |

**`auth_down` 하나가 "텔레그램이 된다"는 인상을 만들었다.** 08-28 거짓 경보가 온
경로가 그것이다. 정작 형님이 실제로 일하는 워크스페이스의 이벤트는 안 갔다.

## 왜 축을 지우는가 — "안 쓰인다" 가 아니라 "구분한 적 없다"

| | 형님 ws | admin ws |
|---|---|---|
| 실제 bound 채널 | `in_app`, **`telegram`** | `in_app`, `telegram` |
| 저장된 매트릭스의 열 | `in_app`, `slack`, `email-sender` | `in_app`, `slack`, `telegram`, `email-sender` |
| 편집 이력 | **한 번도 없음** (06-05 생성 = 갱신) | 1회 (07-20) |

**두 워크스페이스 모두 저장된 매트릭스가 현실과 어긋나 있었다** — 한쪽은 바인딩된
적 없는 유령 열을 들고, 다른 쪽은 **바인딩된 유일한 채널의 열이 없었다.**

⚠️ 나는 admin ws 의 `slack: false` / `telegram: true` 를 보고 *"채널 축을 실제로
쓴다"* 고 결론낼 뻔했다. **`slack` 은 바인딩된 적이 없다.** 그 다름은 의도가 아니라
잔재였다. ⇒ **축이 살아 있는지는 *값이 다른가*가 아니라 *그 다름이 무언가를
바꿨나*로 세라.**

∴ 이 축이 서로 다른 결과를 낸 사례 **0건**. 프로덕션에서 한 일은 **바인딩된 유일한
채널을 조용히 침묵시킨 것**뿐. 관할권 축 · `region`(#845) · canon 만료축(#851)과
같은 모양이다. (형님, 2026-08-31: *"가장 단순한 게 가장 낫다"*)

## 새 형태

**이벤트당 불리언 하나.** 켜면 인박스 + **바인딩된 모든 푸시 채널**, 끄면 아무것도.

`in_app`/`push` 2열로 남기는 안도 검토했지만, 그 구분을 표현한 값들이 전부
**바인딩된 적 없는 채널**의 것이라 의도의 증거가 아니었다.

**이 접기는 버그를 구조적으로 없앤다** — 부재할 채널 키 자체가 사라지므로
"붙였는데 아무것도 안 온다"가 발생할 자리가 없다. 커넥터를 붙이는 것과 그 채널이
받는 것 사이에 **아무 저장 상태도 끼지 않는다.**

## 마이그레이션 — `in_app` 을 승격한다

푸시 채널 값(`slack`/`email-sender`)은 바인딩된 적 없는 채널의 것이라 의도의
증거가 아니다. OR 로 접으면 `email-sender: true` 때문에 `daily_brief` 까지 켜진다
— 아무도 고른 적 없는 결과다. `in_app` 은 그 워크스페이스가 **실제로 도달하는
채널**에 대해 내린 유일한 판단이므로 그것을 스위치로 올린다.

**형님 폰 기준 결과** (dry-run 으로 확인): `needs_you` · `triggered` · `shipped` ·
`failed` 가 텔레그램으로 오고 `daily_brief` 는 안 온다. 그리고 이제 **끄면 실제로
꺼진다**(지금은 켜도 안 켜진다).

## ⚠️ 내가 깨뜨릴 뻔한 것 — "명시적 거부"

첫 구현은 `DEFAULT_ON_EVENTS` 를 **무조건 우선**시켜서, 형님이 `auth_down` 을 꺼도
계속 보냈다. 기존 테스트(`auth_down_still_honours_an_explicit_no`)가 잡았다.

옛 코드의 주석이 그 원칙을 이미 적어 뒀었다 — *"An explicit False is still a No.
This changes the default for a key the founder never set — never a choice they
made."* 기본값은 **부재한** 스위치에만 적용되도록 되돌렸다.

## ⚠️ 광범위 자동 변환에 세 번 당했다

1. **`ast.unparse`** 로 테스트 매트릭스를 변환 → **주석 31개 소실**(570줄 삭제).
   diff 크기가 이상해서 발견, 되돌리고 텍스트 치환으로 재작업(15줄 변경).
   **`ast.unparse` 는 편집 도구가 아니라 전체 재작성 도구다.**
2. **정규식**이 무관한 객체까지 평면화 — `prefs({quiet_hours_enabled: true})` →
   `prefs(true)`, `expect.objectContaining({telegram: true})` → `objectContaining(true)`.
   게다가 `(...)+` 패턴이 **마지막 키만** 봐서 값도 틀렸다. diff 를 한 줄씩 읽어 잡았다.
3. 같은 정규식이 PWA 테스트에서도 오적용 → 되돌리고 **손으로** 고쳤다(11줄).

⇒ **대상이 좁으면 손으로 고쳐라.** 자동 변환의 손익분기점은 생각보다 훨씬 높다.
