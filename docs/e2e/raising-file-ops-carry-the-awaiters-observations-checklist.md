# raise 하는 파일 연산이 awaiter 의 관측을 실어 나른다 — 검증 체크리스트

> 2026-09-09. 다섯 달째 **무관한 PR** 의 CI 를 터뜨려온 실패를 조사하다 나왔다.
> ⚠️ **이 PR 은 그 레이스를 고치지 않는다.** 레이스를 **진단 가능하게** 만든다.

## 먼저 — 내 앞선 진단을 정정한다

같은 세션에서 나는 이 실패를 *"판별기가 침묵했으니 제품 갭"* 이라고 기록했다.
그건 **너무 앞서간 결론이었다.** 실제로 확인된 것은 이것뿐이다:

> **네 모양을 가르는 계측이 존재하는데, CI 가 실제로 터지는 두 경로가 그 값을 버린다.**

어느 모양인지는 **아직 모른다.** 알 수 없게 되어 있었다는 것이 이 PR 의 발견이다.

## 증상 — 다섯 달, 같은 한 줄

```
SandboxError: list_dir '.': exit None
```

`exit None` = `res.timed_out` (제품이 예산을 다 쓰고 포기). 발생 이력(코드 주석에
남아 있다): 2026-08-25 · PR #875 · PR #877 · 2026-09-02(PR #873) · 2026-09-09(PR #903).
**여러 번 docs-only PR 에서** 터졌다.

## 계측은 있었다 — 마지막 홉에서 버려졌을 뿐

`TaskTimeout` 독스트링은 네 모양을 가르는 법을 적어놨다:

| `polls` | `last_status` | 뜻 |
|---|---|---|
| ≈ `timeout_s / 2.0` | `"dispatched"` | 워커가 보고를 안 했다 |
| ≈ 같음 | `None` | **행이 이 읽기에 안 보인다** (DB/세션 가시성) |
| 훨씬 **아래** | — | 대기 루프 자체가 굶었다 |
| — | **terminal** | 행은 done 이었고 모든 읽기가 놓쳤다 ← *"the alarming shape"* |

`exec` 는 이 값들을 `stderr` 에 담아 **돌려준다**. 그런데:

| 같은 파일의 raising 경로 | 타임아웃 시 메시지 |
|---|---|
| 워크트리 프로비저닝 | ✅ `detail = stdout+stderr[-500:]` 를 실어 보냄 |
| **`read_file`** | ❌ `exit {code}` 만 — stderr 버림 |
| **`list_dir`** | ❌ `exit {code}` 만 — stderr 버림 |

**같은 파일, 약 120줄 간격.** 한 실패 경로에서 고친 교훈이 나머지로 안 옮겨간 것이다.
그리고 하네스 쪽에서도 **정확히 같은 모양**이 이미 한 번 났다 — PR #875 의 귀속
로직이 *"반환 경로에만 있어서 raise 하는 호출을 통째로 건너뛰었다"*.
**같은 파일에서, 같은 축(return vs raise)으로, 두 번.**

## 왜 이게 다섯 달을 설명하는가

발생할 때마다 손에 쥔 정보가 `exit None` 뿐이었다 ⇒ 모양을 못 가른다 ⇒ 재현은
70~90초 e2e 라 비싸다 ⇒ **하네스만 단단히 하고 넘어간다.** 그 사이 계측값은
`client_worker_exec_timeout` 로그로 **이미 찍히고 있었지만** 실패 메시지에는 없었다.

## 고친 것

`_failure_detail(res)` — `stdout`/`stderr` 를 이어 마지막 500자를 붙인다. 형제
워크트리 경로의 관용구 그대로다. 평범한 non-zero exit 은 `stderr` 가 비어 있어
**아무것도 안 붙는다**(메시지 회귀 0).

```
list_dir '.': exit None — exec timed out after 90.0s (command budget 30s + 60.0s
    report slack; 17 polls in 33.0s, last status 'dispatched')
read_file 'nope.toml': exit 1          ← 평범한 실패는 그대로
```

## 체크리스트

### 유닛 (자동)

- [x] `list_dir` 타임아웃이 `polls` 와 `last_status` 를 메시지에 싣는다
- [x] `read_file` 타임아웃도 같다 (파라미터화 — 한쪽만 고치는 것이 이 결함의 원형이다)
- [x] **대조군** — 타임아웃이 아닌 평범한 non-zero exit 은 메시지가 그대로다
      (`polls` 가 안 붙는다). 진단을 실어 나르느라 평범한 실패를 흐리면 안 된다
- [x] RED→GREEN 전환으로 실증: 고치기 전 두 테스트가 정확히 이 이유로 빨갛고
      대조군은 양쪽에서 초록. 파일 전체 19/19 통과

### 게이트 (자동)

- [x] `ruff` check+format · `lint-imports` 5/5 · `mypy` 583 clean · 전체 백엔드 스위트

### 라이브 (다음 발생 시 — 이 PR 의 진짜 목적)

- [ ] **다음에 이 테스트가 CI 에서 빨개지면 메시지의 네 숫자를 읽어라.**
      그때 비로소 모양이 정해진다:
      - `last_status='dispatched'` + `polls` 정상 → 워커가 보고 안 함
      - `last_status=None` → **행 가시성** 문제
      - `polls` 가 비율보다 훨씬 낮음 → 러너가 굶음 (하네스/인프라)
      - `last_status` terminal → **행은 done, 모든 읽기가 놓침** ← 가장 위험
- [ ] 그 판정이 나오기 전에는 **레이스의 원인을 단정하지 마라.** 다섯 달 동안
      단정이 다섯 번 빗나갔다
